🔴 **Production bug found while probing — now fixed in PR #37, still live on production until it merges.** `/api/v1/stores` returns `200 []`, so it looks healthy and nothing errors or alerts — it just silently serves an empty catalog. Root cause, confirmed: `api/main.py` loaded the store/product catalog from `products.json` / `stores.json` at the repo root, but those two files were untracked from git in commit `bea05a5`. CI checks out only tracked files → absent from the Docker build context → absent from the running container → the `if path.exists()` guard silently falls through and leaves `app.state.stores = []`. Structural, not a data problem: a rebuild/redeploy would not have fixed it.

[FIXED, PR #37] `/stores`, `/stores/{id}` and `/stores/{id}/items` now read the **RDS catalog** — the same source of truth `/search` already used — and the JSON-loading code is gone. **One thing the mobile team needs to know about the data:** there is no `stores` table in RDS, only `items` (which carries `store_id` and `brand`). So a store is derived from the catalog: `id` = `store_id`, `name` = the brand, `categories` = the categories that store actually stocks. The `description`, `logo_url`, `website_url` and `location` fields come back **`null`** — they have no source of truth anywhere. (The old `stores.json` did populate them, but with placeholder data — Unsplash stock photos as logos and invented descriptions — so restoring it would just have been shipping fake data.) Those four fields are already `Optional` in the `Store` schema, so **the response shape does not change** when someone later adds a real stores table; the nulls just start being populated. Likewise `sizes` and `description` on `StoreItem` are empty/null — no columns for them in the catalog schema.

Is the infrastructure/cdk stack actually DEPLOYED, or only written? **Deployed.** `.github/workflows/deploy-api.yml` runs `cdk deploy --require-approval never` on every push to `main` touching api/ai_engine/infra paths, plus a manual workflow_dispatch trigger for on-demand redeploys. **Rollout note — read before merging PR #37.** First, an open question I couldn't answer without AWS access: **has the index-builder task ever actually been run against the production EFS volume?** If it hasn't, `/recommend` is already broken in production today (no index → the store fails to load → 503 on the fallback path, and the Gemini path fails at its retrieval step too). Worth confirming before assuming the deployed `/recommend` works at all.
Assuming an index does exist on EFS, it was built by the old code, so it has the filename-only mapping. Two consequences: (1) it keeps loading fine after the deploy — the reader still handles old string-format entries — but `/recommend` will keep returning "N/A" fields until the index is rebuilt, so **run the index-builder ECS task, then force a new API deployment** (FAISS is read once at process startup, so a rebuilt index isn't picked up until the API tasks restart); (2) the new load-time consistency check is strict — if the deployed index and mapping are out of sync (e.g. a previously interrupted builder run), the store now refuses to load, surfacing as `/recommend` returning **503** instead of silently returning misaligned products. That's deliberate — loud beats silently wrong — but it means a pre-existing mismatch appears as an outage right after deploy rather than staying invisible. Rebuilding the index clears it.
